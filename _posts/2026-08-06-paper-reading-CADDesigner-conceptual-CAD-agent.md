## 一、研究背景与动机

### 1.1 问题定位
概念设计阶段的 CAD 建模起点是**不完整、抽象的规格描述**（rough idea），设计师需要把模糊意图翻译成精确参数化模型。传统软件（SolidWorks/CATIA 等）门槛高、迭代慢。已有 AI 方法的两条路线各有短板：

1. **参数化生成路线**（DeepCAD/SkexGen/Diffusion-CAD）：只支持 sketch+extrude 等基础操作，表示能力受限；
2. **微调 LLM/VLM 路线**（CAD-Llama/CAD-Recode/Text-to-CadQuery 等）：微调算力贵、高质量 CAD 数据集稀缺、闭源模型不可用。

### 1.3 本文路线
**不训练任何模型**，用商用大模型搭建 ReAct 智能体：文本+草图输入 → 交互式需求细化 → 知识库约束的代码生成 → 视觉反馈迭代纠错。核心配套创新是 **ECIP（Explicit Context Imperative Paradigm）**——一种专为 LLM 生成而设计的 CAD 代码表示范式（工程实现叫 SimpleCADAPI），构建在 CadQuery 之上。

### 1.2 与调研系列工作的本质区别
本文是**概念设计 agent**（模糊意图 → 建模对话 → 近似模型），不是工程图重建（精确图纸 → 精确模型）。这点对需求匹配判断至关重要，见第六节。

## 二、系统架构（ReAct Agent）

### 2.1 为什么用 ReAct 而非硬编码 workflow
工作流用 **prompt 编码**而非程序写死，agent 在运行时解释流程，用户可在任意阶段介入（加约束、纠方向、改目标）——真正可中断的 human-in-the-loop 建模循环：reasoning → acting → reflecting 迭代直到满意。

### 2.2 核心工具链 T = {T1, T2, T3, T4}

| 工具 | 映射 | 功能 |
|------|------|------|
| T1 需求细化 | ℐ → 𝒟 | 多模态输入（文本∅/图像∅ 均可）→ 结构化详细设计规格；用户经修订函数 R: 𝒟×𝒰 → 𝒟 迭代 n 轮得 𝒟_final |
| T2 代码生成 | 𝒟×𝒦 → 𝒞′ | 结合知识库 𝒦 生成 ECIP 代码 |
| T3 命令执行 | 𝒞 → ℳ | shell 执行 Python 代码得 CAD 模型；失败返回结构化错误 |
| T4 视觉反馈 | {ℳ,𝒟} → (P,F) | T4¹: 6 视角渲染（前上左/后下右/后上左/前下右/顶/右）；T4²: 先生成针对性视觉问题 Q（F_vq），再回答得 (P,F)（F_vf）；P=1 终止，P=0 带反馈 F 回到生成 |

闭环：T4² ∘ T3 ∘ T2 ∘ T1: ℐ → 𝒱，P=0 时迭代修正。用户满意（S_at=1）的模型**存入案例库**实现知识积累。除用户环节（R 与 S_at）外，所有状态转移由 agent 自主决定。

### 2.3 辅助工具
- **SketchPad**：键值存储中间数据（图像路径、代码片段、执行结果），支持自动摘要/标签检索/过期清理，解决 agent 上下文爆炸；
- **文件读写工具**：同理避免大段内容反复进上下文。

## 三、ECIP 代码范式（核心创新）

### 3.1 动机：CadQuery 的 Fluent API 对 LLM 不友好
CadQuery 链式调用依赖**隐式内部状态**：$C_{k+1} = f_k(C_k, p_k)$，中间上下文被隐藏，LLM 难以跟踪跨操作的依赖；PythonOCC 类底层 API 虽显式但过于冗长。build123d 用 `@/+/-` 符号运算符，语义对 LLM 不透明。

### 3.2 ECIP 定义
一切操作的输入对象与参数**显式传递**，中间状态是显式变量：

$$S_1 = g_1(S_0, p_1),\ S_2 = g_2(S_1, p_2),\ \dots,\ S_n = g_n(S_{n-1}, p_n)$$

效果：可以用标准 Python 控制流（for 循环、变量赋值）穿插建模，兼具底层 API 的清晰与高层建模的表达力。工程实现 **SimpleCADAPI** 构建于 CadQuery 的 `occ_impl.shapes` 之上，几何类（Vertex/Edge/Wire/Face/Shell/Solid/Compound）是对 CadQuery 对象的轻量封装，完全互操作，兼容 NumPy。

### 3.3 LLM 友好设计三件套

1. **结构化错误信息**（原子操作级三元组）：
   `ErrMsg = (ErrCau, ErrLoc, CorrAct)` —— 根因 / 脚本中精确位置 / 建议纠正动作，替代 CadQuery 笼统的报错；
2. **显式类型标注命名约定**：`ActionName_rReturnType`（如 `make_box_rsolid`、`chamfer_rsolid`），函数名自带返回类型，不看文档也知道类型；
3. **自进化组合操作**：原子操作序列可封装成新操作入库（如螺丝、法兰参数化特征），后续任务直接调用。

### 3.4 SimpleCADAPI 组成
- **Core 模块**：几何对象层级（均继承 `TaggedMixin`）；统一坐标系（`CoordinateSystem` / `WORLD_CS` 全局单例右手系 / `SimpleWorkplane` 上下文管理器支持嵌套局部坐标）；**Metadata & Tagging** 三层机制——① 构造器几何驱动自动打标（如 box 自动标 top/bottom/left/right/side）；② 包装 OpenCASCADE 的 `Modified()/Generated()/IsDeleted()` 计算 **TopoDelta**，布尔/特征操作后自动附加语义标签（`origin.tool`、`op.cut.generated`），避免脆弱的索引记账；③ 结构化几何元数据（尺寸/轴/半径/体积/包围盒等）可序列化；
- **API 模块**：50+ 建模函数分 8 类（创建 25 / 变换 3 / 3D 操作 4 / 布尔 3 / 高级特征 4 / 阵列 2 / 标注选择 14 / 导出 2——支持 extrude/revolve/loft/sweep/fillet/chamfer/shell/helical sweep/pattern 等）；自带**自动化维护管线**（源码解析→函数分类→文档生成→知识库同步）；
- **QL 查询语言**（`ql` 模块）：声明式几何选择，统一"语义血缘查询"（TopoDelta 标签）与"几何属性查询"（如按圆边、按 z 轴中心排序取第一个），selector 可序列化、可回放。

### 3.5 知识库（RAG）
- **组成**：Anno（函数标注：参数格式/返回类型/用法）+ Case（案例，初始人工挑选 + DeepCAD 1K 模型转 ECIP 代码片段，使用中持续增长）；
- **构建**：规则管线从源码注解和 docstring 自动抽取，统一 Markdown 模板（二级标题分块）；
- **检索**：语义友好分块（按 `##` 边界）+ 锚点关键词（如 `[chamfer_rsolid, purpose, chamfer, edge, transition]`）；RAGFlow 实现，bge-large-zh-v1.5 嵌入，向量相似度 0.6 / 关键词 0.4 混合打分，top-k=3。

## 四、实验

### 4.1 设置
- 8 核 CPU 工作站（无 GPU 依赖，全靠 API）；**T2+主 agent = Claude-4-Sonnet，T1+T4 = Gemini-2.5-Flash**；temperature 0.7，top-p 0.9；
- **所有实验关闭用户反馈环**（R 与 S_at），即不含人在环增益；
- 数据：DeepCAD ~178K → SkexGen 协议去重；测试集① 按命令数分层采样 200 个；测试集② 随机 1K（与已有方法对比）；文本输入用 DeepCAD 的 abstract 级描述，图像输入为固定视角单张渲染图。

### 4.2 指标
- 几何：IoU（体素化，voxel=0.02）、CD、HD（2048 采样点）；统一预处理：单位立方体 [−0.5,0.5]³ 归一化 + **ICP 刚性对齐**；
- 过程：Pass@1（一次成功率）、AVG Re（平均重试数）、SUC（可执行建模成功率）、Tokens、Latency。

### 4.3 消融结果

**ECIP 组件消融（200 模型，Table 2）**：

| 变体 | Pass@1 ↑ | AVG Re ↓ | SUC ↑ |
|------|----------|----------|-------|
| 完整 ECIP | **0.45** | **1.86** | **100%** |
| w/o 结构化错误 | 0.41 | 2.62 | 81.5% |
| w/o 类型标注 | 0.32 | 2.30 | 90.5% |

结论分工明确：类型标注保首次准确率（去掉后 Pass@1 大跌），结构化错误保迭代收敛与最终成功率。

**工具与输入模态消融（Table 3）**：

| 变体 | IoU ↑ | CD ↓ | HD ↓ |
|------|-------|------|------|
| A: w/o Anno | 完全失败 | – | – |
| B: w/o Case | 0.2650 | 0.1350 | 0.4690 |
| C: w/o T1 | 0.2726 | 0.1251 | 0.5595 |
| D: w/o T4 | 0.2522 | 0.1192 | 0.4793 |
| E: 纯文本 | 0.3041 | 0.1236 | 0.4154 |
| F: 纯图像 | 0.3518 | 0.1167 | 0.4262 |
| G: 文本+图像 | **0.3893** | **0.0693** | **0.2553** |

要点：Anno 是地基（没有就直接失败）；T4 视觉反馈贡献最大；**图像输入比文本好，文+图最好**（抽象文本本身欠定几何）。

**LLM 后端消融（Table 4）**：Claude-4-Sonnet 0.3041 ≈ Gemini-2.5-Pro 0.2951 ≈ GPT-5.2-Codex 0.2914 —— 性能对后端稳健，ECIP+知识库的贡献大于模型差异。

**推理成本（Fig. 4/5）**：Tokens/Latency 随命令数平缓增长（41+ 命令无陡增）；T2 代码生成占成本大头；单模型平均 ~0.98M tokens / ~436s（ECIP，Table 5）。

### 4.4 对比实验

**表示范式对比（200 模型，Table 5，同 agent 框架只换代码层）**：

| 表示 | IoU ↑ | Pass@1 ↑ | SUC ↑ | Tokens(M) ↓ | Latency(s) ↓ |
|------|-------|----------|-------|-------------|--------------|
| **ECIP** | **0.3041** | 0.46 | **100%** | **0.98** | 436 |
| CadQuery | 0.2827 | 0.50 | 87.5% | 1.40 | 541 |
| build123d | 0.2617 | **0.59** | 96.0% | 1.35 | **363** |

build123d 一次成功率最高、最快，但几何精度最差——"能跑 ≠ 形状对"；ECIP 精度与可靠性最优且最省 token。小提琴图（Fig. 6）显示 ECIP 分布更集中。

**与已有 Text-to-CAD 方法对比（1K 模型，抽象文本，Table 6）**：

| 方法 | IoU ↑ | CD ↓ | HD ↓ | SUC ↑ |
|------|-------|------|------|-------|
| Text2CAD | 0.1831 | 0.1475 | 0.5680 | 96.6% |
| cadrille | 0.0274 | 0.2162 | 0.5817 | 98.2% |
| CADCodeVerify | 0.2348 | 0.2329 | 0.4892 | 86.1% |
| **CADDesigner** | **0.2769** | **0.1097** | **0.4347** | **100%** |

cadrille 的教训很典型：SUC 98.2% 但 IoU 仅 0.027——生成语法有效却语义无关的模型（从专家级指令到抽象指令泛化失败）。图像输入对比（Fig. 8）：CADDesigner 支持 revolve/pattern 等高级操作，对旋转体与重复结构明显优于只会 extrusion 的 cadrille。

### 4.5 局限性（作者自述）
1. 端到端延迟不可忽视（T2 主导），交互场景体验受限；
2. **未纳入工业设计领域知识**：制造约束、公差、装配语义、工程规范均缺失；
3. 复杂工业模型的生成与验证能力仍需提升。

## 五、创新点总结

1. **ECIP 范式**：把"API 表示风格影响 LLM 生成质量"这个直觉做成了系统性工程——显式状态传递 + 类型标注命名 + 结构化错误 + 语义标签血缘（TopoDelta），消融证实每个组件都有独立贡献；
2. **零训练的 agent 路线**：ReAct + RAG 知识库 + 视觉反馈闭环，绕开微调算力与数据集稀缺，性能超所有对比方法（含训练类方法）；
3. **自进化机制**：用户确认的案例入库、组合操作沉淀为新 API，知识库随使用增长；
4. **揭示"语法有效≠语义正确"**：build123d 高 Pass@1 低 IoU、cadrille 高 SUC 低 IoU 两个反例，说明评估 agent 类 CAD 生成必须看几何对齐。

## 六、能否满足你的需求？（需求匹配分析）

先把你的可能需求拆成三种情形，结论不同：

### 情形 A：工程图 → 精确 CAD 重建（你此前调研的主线）
**不匹配。** CADDesigner 的定位是概念设计（abstract text/sketch → 近似模型），不解析带尺寸标注的正交工程图。证据：
- 它的图像输入是单张固定视角渲染图/草图，不是多视图制图；
- 在 DeepCAD 抽象文本上 IoU 只有 0.28–0.39——这是"神似"级别，远达不到 Drawing2CAD（ACC_cmd 82）/ Ortho2CAD（IoU 0.79）那种逐特征对齐的重建精度；
- 若你的目标是"图纸数字化/逆向重建"，继续沿 Drawing2CAD/Ortho2CAD 路线，CADDesigner 不构成替代。

### 情形 B：快速概念原型（"画个光学支架/镜座/样品夹具"级别）
**方向匹配，但落地有现实障碍：**
- ✅ 文本+草图 → 对话式细化 → STEP/STL 导出，正是机械件快速出图的理想形态；fillet/revolve/pattern 等操作齐备，比 DeepCAD 系方法表达力强得多；
- ⚠️ **精度只有 IoU ~0.3 量级**，输出是"需要人工接手修正的草稿"，不能直接进加工；
- ⚠️ **代码未公开**（"available on request"），SimpleCADAPI 拿不到就直接失去复现与二次开发可能；这是四条论文线里开放程度最差的；
- ⚠️ 依赖 Claude-4-Sonnet 等商用 API，单模型 ~0.98M tokens / ~7 分钟延迟，批量使用成本不低；
- ⚠️ 作者自己承认无制造约束/公差/装配语义。

### 情形 C：光子器件/掩膜版图生成（你的专业场景）
**基本不适用。** 输出是 STEP/STL 机械实体，不是 GDSII/掩膜图形；亚微米级精度、周期性超表面阵列这类需求不在其设计目标内。pattern 阵列功能虽然存在，但面向的是机械特征阵列，不是光刻版图。

### 真正值得带走的东西（即使不用这个工具）
1. **ECIP 思想是普适的**："给 LLM 用的代码接口应该显式传状态、类型写进函数名、错误信息结构化"——这条经验对任何 LLM 生成领域代码（包括生成 TMM/RCWA 仿真脚本、实验控制脚本）都直接可用，而且不需要他们的 API，自己包一层就行；
2. **视觉反馈闭环 T4 的问题生成式设计**（先按需求生成检查问题 Q 再逐项回答）比笼统"看看对不对"更可靠，可迁移到任何"生成-渲染-校验"管线；
3. **知识库的工程细节**（`##` 语义分块 + 锚点关键词 + 向量/关键词 0.6/0.4 混合检索）是一份可以直接抄的 RAG 配方；
4. **评估警示**：SUC/Pass@1 与 IoU 可以严重背离（cadrille 98.2% vs 0.027），评估生成式系统必须同时看"能不能跑"和"跑出来像不像"。

**一句话结论**：作为工具——除非你处在情形 B 且能接受"AI 出草稿、人来精修"的模式，否则不建议投入；作为方法参考——ECIP 的 LLM 友好 API 设计原则和视觉反馈闭环值得吸收进你自己的代码生成/仿真自动化工作流。

## 七、与调研系列工作对照

| 维度 | Drawing2CAD | CAD-Coder | Ortho2CAD | **CADDesigner** |
|------|------------|-----------|-----------|-----------------|
| 任务 | 工程图→CAD 重建 | 图像→CAD 代码 | 工程图→CAD 代码 | 模糊意图→概念 CAD |
| 输入 | 4 视图 SVG | 单张渲染图 | 3 视图栅格图纸 | 文本+草图（可空） |
| 输出表示 | DeepCAD 命令序列 | CadQuery | CadQuery | ECIP/SimpleCADAPI（CadQuery 之上） |
| 模型 | 定制 Transformer | LLaVA-13B 微调 | Qwen3-VL-8B SFT+RL | **零训练**（Claude-4-Sonnet agent） |
| 精度指标 | ACC_cmd 82.43 | IoU 0.675 | IoU 0.7922 | IoU 0.28–0.39（量级低，但任务不同） |
| 交互性 | 无 | 无 | 无 | 多轮人在环 |
| 开放性 | 代码+数据开源 | 代码+数据开源 | 管线开源 | **按需索取** |
| 操作覆盖 | line/arc/circle/extrude | 继承 GenCAD 转换 | CadQuery 全集 | extrude/revolve/loft/sweep/fillet/pattern 等 50+ |

**谱系定位**：前三篇都在解决"精确重建"（输入已含完整几何信息），CADDesigner 解决的是上游的"概念生成"（输入本身欠定）。它的对照实验也印证了这一点——它不跟重建类方法比重建精度，而是在"抽象文本输入"这个欠定任务上赢过 Text2CAD/cadrille。四条路线合起来覆盖了设计流程的两端：**概念期用 agent（CADDesigner），工程期用重建模型（其余三篇）**。
